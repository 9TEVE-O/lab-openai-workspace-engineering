# F05 — Read-only migration-state verification

## Requirement

Add a read-only verification mode that checks whether a database's recorded migration state is consistent with the currently discovered migration sets.

Add:

`sqlite-utils migrate DATABASE [PATHS...] --verify-json`

The mode uses the same file discovery, optional `--include-plugin-migrations`, migration-set dependency rules and plan representation as normal migration execution.

It must not execute migration functions.

The JSON result must contain:

- `valid`: boolean;
- `applied`: count of applied migrations that match a currently discovered set/name;
- `pending`: count of currently discovered migrations not yet applied;
- `unknown_applied`: applied `(migration_set, migration_name)` pairs that no longer exist in the discovered migration definitions;
- `dependency_violations`: migration-set dependencies that are not satisfied by the recorded applied state;
- `duplicate_sets`: duplicate migration-set names detected during discovery;
- `cycles`: any dependency cycles;
- `sources`: the distinct file/plugin sources considered.

A database is invalid if any of `unknown_applied`, `dependency_violations`, `duplicate_sets` or `cycles` is non-empty.

Verification of a missing database reports zero applied migrations and the discovered migrations as pending; it must not create the database file.

## Acceptance

1. A fully applied, consistent database reports `valid: true`.
2. A partially applied but dependency-consistent database can still report `valid: true` with a non-zero pending count.
3. An applied migration row whose set/name is absent from current definitions appears in `unknown_applied` and makes the result invalid.
4. An applied dependent-set migration without its required set being fully applied appears in `dependency_violations`.
5. Duplicate set names and dependency cycles are represented in the machine-readable result and make it invalid.
6. No migration function is executed.
7. No database file, migration table, schema object or row is created or modified by verification.
8. Existing migrate behaviour is unchanged when `--verify-json` is not supplied.
9. In the frozen P1 environment, a synthetic fixture containing 100 migration sets with 100 registered migrations each must complete verification in no more than 5.0 seconds and with peak process RSS no greater than 256 MiB. The fixture must use no-op migration functions and a prebuilt migration-history table so the measurement evaluates planning/verification overhead rather than migration execution.

## Boundary

This requirement verifies migration state and dependency consistency only. It does not inspect migration function source for semantic drift and does not execute migrations in a sandbox or dry-run copy.
